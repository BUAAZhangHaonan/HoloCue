# 服务器与内存约束

## 授权范围

4029 项目目录 `/home/hdd3/zhanghaonan/projects/holocue`。计算 GPU 仅物理编号 1、2。默认先用物理 GPU 1 跑 4B，资源不足时检查物理 GPU 2；不允许占用 0、3 及其余设备。GPU 1、2 都被占用时停止模型部署，保留只读盘点结果。

使用 GPU UUID 作为 CUDA_VISIBLE_DEVICES，记录物理编号与 UUID 对照。启动后 cuda:0 是掩码内的逻辑编号，必须能够追溯到获准物理设备。禁止使用 --gpus all。禁止杀掉其他项目、用户或整张卡上的进程。

## 默认项目红线

真实管理员规则未知。先读取服务器现有规范，以两者中更严格者为准。下列数值是本包给出的保守默认值，可进一步收紧，不能作为已知服务器配置引用。

| 资源 | 默认约束 |
|---|---|
| 主机可用内存 | 保留至少 32 GiB 或物理内存的 20%，取较大值 |
| 模型进程树 RSS | 上限 32 GiB |
| API、Viser 各自 RSS | 各 8 GiB |
| Blender 单次构建 RSS | 12 GiB，CPU，4 线程 |
| 引擎显存分配比例 | 默认 0.70，脚本最多接受 0.80 |
| GPU 总显存占用 | 监控到超过 90% 时终止本项目进程组 |
| 模型启动可用显存 | 每张被选择的 GPU 至少 12 GiB，并确认无既有计算任务 |
| 模型上下文和并发 | 8192，1；输出最大 1600 tokens |
| 下载剩余磁盘 | 至少 50 GiB；先查重复模型 |

RSS 按进程树求和，共享页可能重复计数，因此是保守监测。1 秒轮询是监控保护，不能保证杜绝瞬时 OOM；有可用 cgroup 限额时结合使用。不要为通过实验关闭保护。模型启动、编译和首次图像输入均要监测峰值。

## 模型选择

优先 4B 原始 checkpoint 与可复用的既有 vLLM/SGLang 环境；应用与模型依赖分开。9B 为用户授权的另一组实验，需重新核查硬件和显存，可显式选择 GPU 1、2 张量并行。不得同时启动两个超预算实验。

不得未经记录改成其他模型、量化权重、降低图像尺寸或改变提示协议来伪造同一实验成功。硬件不支持 BF16 时，按引擎文档选择可支持的 dtype 并单独记录。参数或模型变更是明确的新配置，不是失败后的静默替换。

## 启动与停止

所有模型启动通过 resource_guard.py。CPU 服务也通过守卫启动，并把 CUDA_VISIBLE_DEVICES 置空。守卫只管理它创建的进程组，不执行 pkill、killall、GPU reset 或系统清理。

进程由执行工具的长期终端、tmux 或明确的进程管理器托管，记录每个服务 PID 与日志路径。停止仅针对已记录的本项目进程。对外示例使用 SSH 隧道，服务不默认绑定 0.0.0.0。
